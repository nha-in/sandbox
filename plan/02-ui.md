# 02 — UI: Templates, htmx, Design System, Docs Portal

**Parent:** [00-master-plan.md](00-master-plan.md) · **Audience:** engineers building screens (full-stack Django — no separate frontend team) · **v0 tickets:** [C3–C9](v0-tickets/README.md)

---

## 1. In plain words

There is no separate frontend application. Django renders every page as HTML on the server; **htmx** (a small JS library driven by HTML attributes) upgrades pages in place — submitting a form without a full reload, polling a status badge — but nothing _depends_ on it: every button and form works with JavaScript switched off. Styling is Tailwind through a small house vocabulary of `ui-*` classes (`ui-card`, `ui-btn--primary`, …) so screens look consistent without a component library. The only real JavaScript component in the product is the API-docs viewer (v1).

## 2. Legacy findings

CRA 5 (EOL), dual MUI v4+v5 (~400KB waste), 23 Redux reducers acting as an invalidation-free server cache, ~3,300 lines of duplicated wizard forms, JWTs in localStorage, gateway keys in the bundle. **v2 removes the SPA class entirely.** Product mockups exist as directional references, not pixel specs — the current set is held outside this repo, along with a table of the places they contradict decisions already settled here.

## 3. Design

### 3.1 Stack (as built in V0.1)

| Concern       | Choice                                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Templates     | Django templates; djLint formatted/linted                                                                                  |
| Interactivity | htmx (vendored to `sandbox/static/js/vendor/`), django-htmx middleware; CSRF via `hx-headers` on `<body>`                  |
| Styling       | Tailwind v4 via django-tailwind-cli standalone binary (no node in prod images)                                             |
| Components    | careui design system ported from the care ecosystem (`careui.css` + tokens; `@utility`-declared — Tailwind v4 requirement) |
| Forms         | Django forms rendered with the `{% ui_field %}` templatetag (`sandbox/theme`) — never hand-written widget classes          |
| JS islands    | exactly one planned: rapidoc docs viewer (v1). Anything else needs an ADR                                                  |
| i18n / a11y   | `{% translate %}` from day one; skip links, aria-current nav, `prefers-reduced-motion`                                     |

### 3.2 htmx conventions

1. **Nothing depends on htmx.** Every action keeps a real `action=` and answers a plain POST with a redirect; `hx-*` upgrades in place.
2. Partials are templates in `partials/`, rendered by the same view module as the page; swap targets by stable `id`.
3. **Polling for async state:** a fragment re-polls while pending — `hx-get … hx-trigger="every 4s" hx-swap="outerHTML"` — and stops rendering the trigger at terminal states. Degrades to plain refresh.
4. Busy states: `hx-disabled-elt="this"` + `.htmx-indicator`; shared `#nav-progress` for boosted navigation.
5. Messages framework renders into `components/messages.html`; htmx responses may OOB-swap it.

### 3.3 Layout shells (built in V0.1)

`layouts/marketing.html` (public) · `layouts/app.html` (signed-in integrator: sidebar, `#main-content`) · `layouts/console.html` (staff/reviewer, only under the console gate) · `layouts/error.html` (403/404/500).
